# TanStack Query 도입 검토

## 현재 상태 분석

### 현재 데이터 페칭 패턴

프로젝트는 현재 클라이언트 컴포넌트에서 직접 `fetch` API를 사용하고 있습니다:

**주요 특징**:
- `useState`와 `useEffect`로 데이터 로딩 관리
- 각 컴포넌트마다 로딩/에러 상태를 개별적으로 관리
- 데이터 갱신을 위해 수동으로 함수 호출 (`loadExpenses`, `loadIncomes` 등)
- 캐싱이나 자동 재시도 로직 없음
- 여러 컴포넌트에서 같은 데이터를 요청할 때 중복 요청 발생

**예시 코드** (`app/book/page.tsx`):
```typescript
const [expenses, setExpenses] = useState<ExpenseItem[]>([]);
const [isLoading, setIsLoading] = useState(true);

useEffect(() => {
  const loadData = async () => {
    try {
      const response = await fetch(`/api/book/${id}/expense?...`);
      const data = await response.json();
      setExpenses(data.expenses || []);
    } catch (error) {
      toast.error("지출 목록을 불러오는데 실패했습니다.");
    } finally {
      setIsLoading(false);
    }
  };
  loadData();
}, [selectedDate, bookId]);
```

### 현재 문제점

1. **코드 중복**: 로딩/에러 처리가 각 컴포넌트마다 반복됨
2. **캐싱 없음**: 같은 데이터를 여러 번 요청 (예: 예산 페이지와 지출 페이지에서 같은 지출 데이터 요청)
3. **낙관적 업데이트 없음**: 사용자 액션 후 즉시 UI 업데이트 불가
4. **백그라운드 리프레시 없음**: 탭 전환 시 항상 새로고침
5. **중복 요청**: 여러 컴포넌트에서 같은 API를 호출할 때 중복 요청 발생
6. **에러 재시도 없음**: 네트워크 오류 시 자동 재시도 없음
7. **로딩 상태 관리 복잡**: 여러 데이터를 동시에 로드할 때 상태 관리가 복잡함

## TanStack Query 도입의 장점

### 1. 자동 캐싱 및 동기화
- 같은 쿼리를 여러 컴포넌트에서 사용해도 한 번만 요청
- 캐시된 데이터를 즉시 반환하여 UX 개선
- 여러 컴포넌트 간 데이터 자동 동기화

### 2. 자동 백그라운드 리프레시
- 포커스 시 자동으로 최신 데이터 가져오기
- 네트워크 재연결 시 자동 리프레시
- 설정 가능한 리프레시 간격

### 3. 낙관적 업데이트 (Optimistic Updates)
- 사용자 액션 후 즉시 UI 업데이트
- 서버 응답 후 실제 데이터로 교체
- 사용자 경험 크게 개선

### 4. 자동 재시도 및 에러 처리
- 네트워크 오류 시 자동 재시도
- 일관된 에러 처리 패턴
- 재시도 간격 자동 조정

### 5. 코드 간소화
- 로딩/에러 상태 자동 관리
- 중복 코드 제거
- 선언적 데이터 페칭

### 6. 개발자 경험 개선
- DevTools로 쿼리 상태 시각화
- 디버깅 용이
- 타입 안정성 (TypeScript 지원)

## TanStack Query 도입의 단점

### 1. 학습 곡선
- 팀원들이 새로운 개념 학습 필요
- 쿼리 키 관리, invalidation 등 개념 이해 필요

### 2. 번들 크기 증가
- 약 13KB (gzipped) 추가
- 하지만 캐싱으로 인한 네트워크 요청 감소로 상쇄 가능

### 3. 초기 설정 필요
- QueryClient 설정
- Provider 설정
- 기본 옵션 설정

### 4. 마이그레이션 작업
- 기존 코드 리팩토링 필요
- 테스트 코드 수정 필요

## 추천 도입 시점

### **Phase 5 (대시보드) 시작 전 도입을 추천합니다**

**이유**:

1. **현재 시점이 적절함**
   - Phase 3-4의 핵심 기능이 완료되어 안정화됨
   - 코드베이스가 아직 크지 않아 마이그레이션 부담 적음
   - Phase 5부터 새로운 패턴 적용 가능

2. **대시보드 개발에 유리**
   - 대시보드는 여러 데이터 소스를 동시에 표시
   - TanStack Query의 캐싱과 동기화 기능이 매우 유용
   - 백그라운드 리프레시로 항상 최신 데이터 유지

3. **점진적 마이그레이션 가능**
   - Phase 5부터 새 기능에만 적용
   - Phase 3-4 코드는 필요 시 점진적으로 리팩토링
   - 기존 기능 동작에 영향 없음

4. **공동 가계부 개발 준비**
   - Phase 6에서 실시간 동기화가 필요할 때 이미 도입되어 있음
   - 낙관적 업데이트로 사용자 경험 개선

## 도입 계획

### 1단계: 기본 설정 (1-2시간)
- `@tanstack/react-query` 설치
- QueryClient 설정
- Provider 설정 (`app/layout.tsx`)
- 기본 옵션 설정 (staleTime, cacheTime 등)

### 2단계: 핵심 기능 마이그레이션 (4-6시간)
- 가계부 목록 조회 (`/api/book`)
- 지출 목록 조회 (`/api/book/[bookId]/expense`)
- 수입 목록 조회 (`/api/book/[bookId]/income`)
- 예산 목록 조회 (`/api/book/[bookId]/budget`)

### 3단계: Mutation 구현 (2-3시간)
- 지출 추가/수정/삭제
- 수입 추가/수정/삭제
- 예산 추가/수정/삭제
- 낙관적 업데이트 적용

### 4단계: Phase 5 개발 시 적용 (지속)
- 대시보드 데이터 페칭
- 통계 데이터 페칭
- 새로운 기능에 바로 적용

### 5단계: 점진적 리팩토링 (선택사항)
- Phase 3-4 코드를 필요 시 리팩토링
- 우선순위 낮은 작업으로 진행

## 예상 효과

### 개발 생산성
- 데이터 페칭 코드 50-70% 감소
- 버그 발생 가능성 감소 (캐싱, 동기화 자동화)
- 개발 속도 향상 (새 기능 개발 시)

### 사용자 경험
- 페이지 전환 시 즉시 데이터 표시 (캐시 활용)
- 백그라운드에서 자동으로 최신 데이터 가져오기
- 낙관적 업데이트로 반응성 향상
- 네트워크 오류 시 자동 재시도

### 성능
- 중복 요청 제거로 네트워크 요청 감소
- 캐싱으로 불필요한 API 호출 감소
- 번들 크기 증가는 있으나 네트워크 요청 감소로 상쇄
